## Functional Requirements
- FR-001 (maps S3-AC1): The system SHALL provide a migration or schema initialization script that, when executed as part of the project’s standard DEFAULT schema setup, creates a table named DEFAULT.mfa_setting_change_email_records if it does not already exist.
- FR-002 (maps S3-AC1): The DEFAULT.mfa_setting_change_email_records table SHALL define columns and data types that are consistent with the existing DEFAULT.registration_email_records and DEFAULT.account_deletion_notification_records tables, including but not limited to: a primary identifier column, a user reference (such as user_id or equivalent), one or more status fields suitable for outbox processing, created/updated or equivalent timestamp columns, and explicit fields to store the MFA change type and the MFA change timestamp. Any ambiguities in exact column names or types MUST be resolved by aligning with the existing email outbox tables’ conventions rather than introducing a new pattern.
- FR-003 (maps S3-AC2): The migration or schema script suite for DEFAULT.mfa_setting_change_email_records SHALL be idempotent under the project’s existing execution model such that re-running it in an environment where DEFAULT.mfa_setting_change_email_records already exists completes successfully without fatal errors.
- FR-004 (maps S3-AC2): The migration or schema script for DEFAULT.mfa_setting_change_email_records SHALL NOT drop, truncate, or re-create the table in a way that would delete or corrupt existing rows, and SHALL leave the table’s structure in a state that remains compatible with its intended outbox usage after re-execution.
- FR-005 (maps S3-AC3): After the migration has been applied, the application, when configured with better-sqlite3 and using the same database connection configured for other DEFAULT.* tables, SHALL be able to successfully execute at least basic INSERT and SELECT operations against DEFAULT.mfa_setting_change_email_records without runtime errors.
- FR-006 (maps S3-AC4): Applying the new migration for DEFAULT.mfa_setting_change_email_records in an environment that already contains production-like data in DEFAULT.registration_email_records and DEFAULT.account_deletion_notification_records SHALL NOT alter the schemas of those existing tables, SHALL NOT modify or delete their existing data, and SHALL NOT introduce failures into existing logic that currently reads from or writes to those tables.
- FR-007 (maps S3-AC4): Any regression or integration testing associated with applying the DEFAULT.mfa_setting_change_email_records migration in an environment where registration_email_records and account_deletion_notification_records are in use SHALL confirm that registration and account deletion email flows continue to behave as before, with no new errors attributable to the presence of the new MFA email record table or its migration.
