# Feature Specification: b4b3c394-8366-5e90-b9d0-ab78e8cb980a

## User Scenarios & Testing
- **S4-AC1**: Given the backend is started with an environment variable defined for the MFA setting-change SendGrid template ID, when the email dispatch service is initialized, then it loads this MFA template ID from the environment (via dotenv) and exposes it through its configuration or types for use by calling code.
- **S4-AC2**: Given the email dispatch service is asked to send an MFA setting-change notification through EmailDeliveryPort with valid input parameters, when it composes the SendGrid request, then it selects the dedicated MFA template (using the configured template ID) rather than reusing registration or account deletion templates.
- **S4-AC3**: Given the codebase type definitions or configuration objects for email templates, when a developer references the MFA template in strongly-typed code, then TypeScript (or equivalent typing) recognizes the MFA template as a distinct, type-safe option (e.g., via an enum member or typed config entry) and rejects invalid template keys at compile time.
- **S4-AC4**: Given the SendGrid API key and MFA template ID are provided via environment variables, when the codebase is scanned or reviewed, then there are no hard-coded SendGrid secrets or template IDs related to MFA notifications checked into source control.
- **S4-AC5**: Given the application is started without the MFA template ID environment variable, when the email dispatch service initializes or when an MFA email send is attempted, then the behavior clearly fails fast or surfaces a configuration error in logs without crashing unrelated profile or authentication flows, allowing operators to detect and remedy the misconfiguration.

## Functional Requirements
- FR-S4-AC1-001: The email dispatch service initialization must read the MFA setting-change SendGrid template ID from a specific environment variable using the existing dotenv-based mechanism whenever that variable is defined at backend startup.
- FR-S4-AC1-002: After initialization, the loaded MFA template ID must be stored in a configuration object or type that is accessible to calling code (including the EmailDeliveryPort implementation) without re-reading the environment on every call.
- FR-S4-AC2-001: When EmailDeliveryPort (or its SendGrid adapter) is invoked to send an MFA setting-change notification with valid input, it must select the dedicated MFA template by setting the SendGrid request's templateId (or equivalent field) to the configured MFA template ID value.
- FR-S4-AC2-002: For MFA setting-change notifications, the SendGrid adapter must not reuse or fall back to existing registration or account deletion template IDs when a valid MFA template ID is available in configuration; any inability to resolve the MFA template ID must be treated as a configuration error rather than silently using another template.
- FR-S4-AC3-001: The set of supported email templates must include a distinct, named entry for the MFA setting-change template in a strongly-typed construct (such as a TypeScript enum, union type, or typed configuration map) that is used wherever templates are referenced in code.
- FR-S4-AC3-002: The compilation or type-checking process must fail when code attempts to reference a non-existent email template key, ensuring that only the defined MFA template identifier (and other allowed templates) can be used at compile time.
- FR-S4-AC4-001: The SendGrid API key and the MFA setting-change template ID must only be obtained via environment-variable access (e.g., process.env through dotenv) and must not be present as string literals or other hard-coded values anywhere in the source code or committed configuration files.
- FR-S4-AC4-002: The project must retain or adopt practices (such as code search or automated checks) that make it possible, during code review or scanning, to verify that no hard-coded SendGrid secrets or MFA-related template IDs exist in the repository, acknowledging that this requirement does not prescribe a specific tool.
- FR-S4-AC5-001: If the backend starts without the MFA setting-change template ID environment variable defined, the email dispatch service must detect the missing configuration at initialization or on first MFA email send attempt and emit a clear, operator-visible error or log message indicating the missing MFA template configuration.
- FR-S4-AC5-002: When the MFA template ID is missing or invalid, attempts to send MFA setting-change notifications must fail in a controlled manner (e.g., by throwing or returning a handled error from the email layer) without terminating the process or causing unrelated profile or authentication API endpoints to crash.
- FR-S4-AC5-003: The absence or misconfiguration of the MFA template ID must not prevent non-MFA-related emails (such as OTP or password recovery) from being sent, provided their own configuration is valid, nor may it interfere with the normal operation of unrelated profile or auth flows.
