## Functional Requirements
- FR-001 (S1-AC1): The system SHALL provide a migration script named as migration 009 in the project's migrations directory, following the project's established naming convention and containing both up() and down() (or equivalent) functions in the format required by the existing migration tooling, such that it is syntactically valid and executable by that tooling.
- FR-002 (S1-AC2): When the up() function of migration 009 is executed against a fresh SQLite database that already contains the otp_requests table, the migration SHALL add an attempt_count column to otp_requests with data type INTEGER, default value 0, and NOT NULL constraint, and SHALL add a verified column to otp_requests with data type BOOLEAN (or the project's boolean representation), default value false, and NOT NULL constraint.
- FR-003 (S1-AC3): When the down() function of migration 009 is executed on a database where the up() function has been successfully applied, the migration SHALL remove the attempt_count and verified columns from the otp_requests table so that the table schema matches its state immediately prior to applying migration 009.
- FR-004 (S1-AC4): When migration 009 up() is executed against a copy of the current production database containing existing otp_requests records, the migration SHALL complete without errors, SHALL preserve all existing column values for each otp_requests row (including user_id, code, expires_at, created_at, and any other pre-existing columns), and SHALL create attempt_count and verified columns populated with default values 0 and false respectively for all existing rows.
- FR-005 (S1-AC5): When the down() function of migration 009 is executed against a production database copy on which the up() function has been applied, the migration SHALL complete without errors, SHALL drop the attempt_count and verified columns from otp_requests, and SHALL leave all other otp_requests data intact so that the schema and data match the pre-migration state (subject to the ambiguity that any data written only to attempt_count or verified will necessarily be lost when those columns are dropped).
- FR-006 (S1-AC6): Migration 009 SHALL be idempotent with respect to the migration framework, such that running the migration process twice in sequence on the same database does not raise an error on the second execution and leaves the otp_requests schema unchanged after the first successful application (noting the ambiguity that, depending on the migration framework, idempotency may be achieved by recording applied migrations rather than making the SQL statements themselves re-runnable).
